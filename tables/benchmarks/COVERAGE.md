## Essential source we could not fetch

**Artificial Analysis** (`artificialanalysis.ai`) is the one source that would directly
answer the "speed/latency" skill (tokens/s, time-to-first-token) in addition to its own
Intelligence Index and Coding Index, across almost our entire model list. Its API requires
an `x-api-key` header — there is a free tier (public docs describe roughly 1,000
requests/day) but it still requires creating an account to get a key, which violates the
"no API keys, no signups" rule for this task, so it was not called. If that rule is ever
relaxed for this router, Artificial Analysis should be the first addition — it would
directly fill the speed/latency gap that `aider_polyglot_seconds_per_case` only partially
covers (that metric is coding-task latency for one specific harness, not a general
tokens/s figure).

## Name-matching pitfalls for whoever builds the router's matching logic

1. **Reasoning-effort / thinking suffixes are not standardized across sources.**
   - Epoch's `model_version` uses `_low/_medium/_high/_xhigh/_max/_none/_unknown` suffixes
     (e.g. `kimi-k3_max`).
   - LiveBench uses `-max-effort`, `-xhigh-effort`, or sometimes just `-max`/`-xhigh` with
     no `-effort` suffix depending on the model family.
   - LMArena's `text`/`webdev`/`text_style_control` configs use lowercase kebab tags like
     `-high`, `-max`, `-xhigh` appended directly to the slug (e.g. `claude-opus-5-max`).
   - LMArena's `agent` config instead uses Title Case with a parenthetical:
     `Claude Fable 5.1 (Max)`, `GPT 6 Astra (Max)`.
   - A router doing exact-string matching across sources will silently miss most
     cross-source joins unless it normalizes case, punctuation, and effort-tag position
     first.

2. **Dates and "(codex-harness)" / "(thinking-...)" annotations are appended inconsistently.**
   Examples actually seen in scores.csv: `claude-haiku-4-5-20251001` (date-stamped),
   `gpt-5.6-sol-xhigh (codex-harness)` (harness-annotated — this is the *same* underlying
   model as `gpt-5.6-sol-xhigh` scored elsewhere, just evaluated through a different coding
   harness on the WebDev arena), `gemini-3-flash (thinking-minimal)`. Strip parentheticals
   and trailing date stamps before joining across sources, but keep them available for
   provenance since they can represent a materially different score (harness-dependent).

3. **"Lite" and non-"lite" variants look similar but are different models.**
   `gemini-3.5-flash` vs `gemini-3.5-flash-lite` are distinct entries in every source that
   has them — don't substring-match `3.5-flash` and accidentally merge them.

4. **Version-number adjacency is not equivalence.** `Qwen3.5-27B` is present in LMArena but
   NOT in Epoch's CSV (which has 9B/35B-A3B/397B-A17B for the 3.5 line instead); LiveBench's
   closest neighbor is `qwen3.6-27b` (a different minor version, 3.6 not 3.5). Don't let a
   fuzzy matcher conflate `qwen3.5-27b` and `qwen3.6-27b` — they are different releases.

5. **SWE-bench Verified rows are (agent scaffold + model) pairs, not pure model scores.**
   The same model can appear many times in `swebench_verified` / the `SWE-Bench verified`
   rows inside `epoch_eci` with very different `resolved` percentages depending on which
   agent harness drove it (e.g. "Sonar Foundation Agent + Claude 4.5 Opus" vs. a mini-SWE-agent
   run of the same model). If the router wants "how good is this model at agentic coding"
   rather than "how good is this specific agent+model combo," it should take the max (or a
   documented top-N) over rows sharing a model, not an arbitrary/first row.

6. **Epoch's `performance` column is not on one universal scale.** It's each benchmark's
   own native score — mostly 0-1 accuracy/pass-rate, but always check `unit` conceptually
   per `benchmark` before comparing across benchmarks (a 0.6 on `HLE` and a 0.6 on `MMLU`
   represent very different difficulty levels). `scores.csv` labels these all as
   `epoch_performance_0_1` for the column type, but that does NOT mean the numbers are
   cross-benchmark comparable — only cross-model-within-the-same-benchmark comparisons are
   valid without further normalization.

7. **Small open-weight models (Qwen3 8B/14B) only show up in Epoch's CSV.** None of the
   arena or agentic sources evaluate them (those track frontier hosted APIs), so any router
   logic that requires "at least 2 independent sources agree" will always fail these two
   models even though they do have one legitimate public score each.
