## 1. The trade-off, stated plainly

Either blend setting **raises teacher under-routing above live**: .099 (t0.3) or .107 (t0) against .059. Under-routing means
a task is sent to a weaker model than it needs. In return, teacher band accuracy rises about 10 points (.576 → .68), teacher
over-routing falls about 15 points (.365 → .21), and on the 83 real-task outcomes accuracy rises .398 → .554 and over-routing
falls .506 → .337.

On real tasks, under-routing is **one task worse**: 9 of 83 against 8 of 83. The gate allows exactly one task of noise, and
this candidate sits **on** that bound, not inside it.

Why the gate allowed it. `s1/evaluate.py` `promotion_report` used the outcome-led rule, because the outcome holdout
n = 83 ≥ `MIN_OUTCOME_HOLDOUT` 50. Every check passed:

| check | rule (evaluate.py) | t0.3 | t0 |
|---|---|---|---|
| outcome under-routing | candidate ≤ live + 1/n (0.0120) | .1084 ≤ .1084 ok (boundary) | same |
| outcome over-routing | live − candidate ≥ `OUTCOME_OVER_MIN_DROP` 0.05 | .506 − .337 = .169 ok | same |
| outcome band accuracy | candidate ≥ live (raw counts) | 46 ≥ 33 hits ok | same |
| teacher under-routing | candidate − live ≤ `TEACHER_UNDER_MAX_RISE` 0.07 | .099 − .059 = .040 ok | .107 − .059 = .048 ok |
| teacher band accuracy | candidate ≥ live − 0.03 if under improves, else − 1/n (0.0011) | .681 ≥ .5749 ok | .680 ≥ .5749 ok |
| outward recall | candidate ≥ `OUTWARD_RECALL_FLOOR` 0.85 | .918 ok | .918 ok |

`TEACHER_UNDER_MAX_RISE = 0.07` is the owner decision of 2026-11-07: real-task outcomes lead, and the teacher's reading is a
proxy tolerated up to a 7-point rise. The unblended candidate (`cand-t0`, teacher under .133, a rise of .074) failed this
check. That failure is why the sweep was run.

## 2. How a sweep setting becomes live (and why a helper is needed)

- **What serves.** `com.cortados.s1-scorer` runs `~/cortados/.venv-mlx/bin/python ~/cortados-router/s1/serve.py`. Its first
  request after `s1/current.json`'s mtime changes reloads `base`, `adapter` and `temperatures` (`ensure_loaded`, about 1.5 s).
  **No restart is needed.** It reads no other pointer field.
- **Fields.** `temperatures` are per-question softmax temperatures, applied inside `student.Scorer.score`. For a sweep
  version they are the ones calibrate.py fitted on the valid split (`runs/2026-11-08/sweep/blend0.7/temps.json`), not
  live's. The blend weights are not a setting: the blend is baked into the adapter file (`sweep/blend0.7/adapters.safetensors`,
  LoRA rank 16 = 8 + 8, the two adapters concatenated along the rank axis). `inference.fail_up_below` and `outward_at` are
  informational. The router hosts apply their own `CORTADOS_S1_FAIL_UP` / `CORTADOS_S1_OUTWARD_AT`, whose defaults (0.75 /
  0.25) are what the sweep graded with.
- **The nightly does not do this itself.** calibrate.py "NEVER promotes and never writes the serving pointer". The nightly
  publishes only through `nightly_state.promote <report.json>`, which needs an evaluate.py report, and a sweep writes none.
  A manual step is needed.
- **Helper.** `s1/promote_sweep.py` (this branch; tests in `tests/test_s1_promote_sweep.py`). `plan` is a dry run by
  default. It refuses a tilted setting, a setting whose `promotion_report` did not promote, a live pointer or weights that
  changed since the sweep, an incomplete or inconsistent version cache, a version without recorded provenance, temperatures
  in `temps.json` other than the ones the scores used, and an adapter whose `adapters.safetensors` / `adapter_config.json`
  sha256 or config content differs from the sweep's record. `plan --write` does three things:
  - copies the adapter, verified by sha256 and made read-only, to `runs/2026-11-08/promoted/2026-11-08-blend0.7/adapter`;
  - keeps `current.json.prev`;
  - writes the pointer atomically, as a nightly promotion does.

  The copy is needed for two reasons. A later sweep of the same candidate rebuilds `sweep/blend0.7/adapters.safetensors` in
  place, which would silently change the served weights at the next scorer restart. And evaluate.py keys its incumbent bar
  cache by the adapter's parent dir name (`data/bar-<name>-<hkey>.json`), so that name must be unique.

  `check` scores holdout rows through the live scorer the way the router does (`core.decide_s1` plus `core.resolve`) and
  compares each band with the sweep's per-row record, by id, printing no request text. It forces
  `CORTADOS_SCARCITY_REFRESH=off`. A selected row missing from `requests.jsonl` counts as a failure (`NOT CHECKED`), as does
  a degraded answer: exit 0 only when every selected row was scored and matched.
- **Hold switch.** `s1/data/no-promote` (this branch, nightly.sh header "Hold promotion", ROUTER-DESIGN §4d). nightly.sh checks
  it immediately before both of its promotion calls. A passing candidate keeps its report and stays pending with reason
  `promotion_held`; once the flag is removed the next in-window cycle always re-evaluates it against the current incumbent and
  holdouts and publishes it only if the fresh report promotes. It does not stop `promote_sweep.py` (a manual publication).

## Part H. The holds stay (owner decision, 2026-11-11)

- `data/no-train-tonight` and `data/no-promote` stay until the **rank-16 warm-start question** is fixed in code and deployed.
  The question: a new run copies the pointer's `adapters.safetensors` as its warm start (`CORTADOS_S1_INIT`). After Part F that
  is the blend, LoRA rank 16 (8 + 8). The run then trains at mlx_lm's default rank 8, and mlx_lm 0.31.3 resumes with
  `model.load_weights(..., strict=False)`, which does not check shapes, so it would likely train rank-16 tensors under a rank-8
  `adapter_config.json`. Nobody has tested this. The fix decides it (refuse a rank mismatch, or warm-start from the
  candidate's own rank-8 adapter).
- Meanwhile the pending `runs/2026-11-10` is evaluated in the first free night window against the incumbent of that night (the
  blend, after Part F). A pass is held: `PROMOTION HELD`, `data/pending-candidate` = `... promotion_held runs/2026-11-10`,
  status.json `last_promotion_held`. A fail drops it ("no longer promotes"). Either way nothing is published and nothing
  trains.
- Lifting, later and only after the fix is deployed: look at `cat $TR/data/pending-candidate` and the held run's
  `report.json` first. `mv $TR/data/no-promote $TR/data/no-promote.lifted-$(date +%F)`: the next in-window cycle re-evaluates a
  held candidate against the current incumbent and holdouts and publishes it only if that fresh report promotes. To discard
  it in favour of new training instead, `touch $TR/data/force-train` before lifting. Then
  `mv $TR/data/no-train-tonight $TR/data/no-train-tonight.lifted-$(date +%F)`.
